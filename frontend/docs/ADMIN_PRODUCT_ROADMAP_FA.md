# نقشه راه پنل ادمین و پشتیبانی Athenlio

وضعیت: برنامه‌ریزی‌شده برای نسخه واقعی؛ خارج از MVP تمرینی فعلی
اصل اجرایی: هیچ صفحه ادمین نمایشی پیش از وجود API امن، RBAC و audit log ساخته نمی‌شود.

## هدف محصول

پنل ادمین باید یک فضای عملیاتی برای رسیدگی به گزارش کاربران، تأیید مدرس‌ها، کنترل محتوا و بررسی رویدادهای حساس باشد؛ نه فقط داشبوردی با چند نمودار. کاربر بتواند از داخل محصول مشکل را با زمینه کافی گزارش کند و تیم پشتیبانی چرخه کامل دریافت، بررسی، پاسخ و بستن مشکل را مدیریت کند.

## نقش‌ها و سطح دسترسی

| نقش | دسترسی اصلی | محدودیت ضروری |
|---|---|---|
| Support | مشاهده و پاسخ به تیکت‌ها | بدون دسترسی به رمز، توکن یا عملیات مالی حساس |
| Moderator | بررسی مدرس، دوره و وبلاگ | بدون تغییر تنظیمات سامانه |
| Admin | مدیریت کاربران، محتوا و وضعیت تیکت | عملیات حساس با ثبت audit log |
| Super Admin | مدیریت نقش‌ها و تنظیمات امنیتی | MFA اجباری و دسترسی بسیار محدود |

مجوزها باید در بک‌اند enforce شوند. پنهان‌کردن دکمه در فرانت‌اند کنترل امنیتی محسوب نمی‌شود.

## ماژول ۱: گزارش مشکل توسط کاربر

فرم «گزارش مشکل» برای کاربر واردشده:

- دسته: حساب، ثبت‌نام، پرداخت/رسید، دوره، استاد، محتوا یا مشکل فنی
- عنوان و شرح مشکل
- پیوست تصویر با محدودیت نوع و حجم
- URL و شناسه منبع مرتبط به‌صورت خودکار
- نسخه مرورگر، زبان رابط و زمان رخداد
- رضایت صریح برای ارسال داده‌های فنی
- شماره پیگیری و تاریخچه پاسخ‌ها

وضعیت‌های تیکت: `new`, `triaged`, `in_progress`, `waiting_for_user`, `resolved`, `closed`, `duplicate`.

## ماژول ۲: صف پشتیبانی ادمین

- فیلتر براساس اولویت، دسته، وضعیت، مسئول و بازه زمانی
- جست‌وجو با شماره تیکت، ایمیل یا شناسه منبع
- تخصیص مسئول و SLA
- یادداشت داخلی جدا از پاسخ قابل‌مشاهده کاربر
- ادغام گزارش‌های تکراری و لینک‌کردن به bug/issue فنی
- ثبت تمام تغییرات مهم در audit log

## ماژول ۳: مدیریت و moderation

- تأیید یا رد پروفایل مدرس همراه دلیل مستند
- تعلیق و فعال‌سازی حساب با گردش تأیید برای عملیات پرریسک
- بررسی دوره‌ها و مقاله‌های گزارش‌شده
- مشاهده ثبت‌نام‌ها فقط در حد لازم برای پشتیبانی
- حذف نرم (soft delete) و امکان بازیابی به‌جای حذف دائمی فوری

## APIهای لازم پیش از ساخت UI ادمین

| حوزه | قرارداد پیشنهادی |
|---|---|
| تیکت کاربر | `POST /api/me/support-tickets/`, `GET /api/me/support-tickets/` |
| گفت‌وگوی تیکت | `POST /api/me/support-tickets/{id}/messages/` |
| صف ادمین | `GET /api/admin/support-tickets/`, `PATCH /api/admin/support-tickets/{id}/` |
| گزارش محتوا | `POST /api/me/reports/` |
| پروفایل مدرس امن | `GET/PATCH /api/tutors/me/profile/` |
| moderation | endpointهای جداگانه ادمین برای تأیید/تعلیق، نه ViewSet عمومی |
| audit | `GET /api/admin/audit-events/` با دسترسی محدود |

هر endpoint باید pagination، validation، object-level permission، rate limiting و قرارداد خطای یکسان داشته باشد.

## الزامات امنیتی Gate انتشار

- RBAC و object ownership در بک‌اند با تست خودکار
- MFA برای Admin و Super Admin
- session کوتاه‌تر برای فضای ادمین و محافظت CSRF/CORS صحیح
- rate limit و ضداسپم برای گزارش‌ها و پیوست‌ها
- اسکن و ذخیره امن فایل‌ها؛ عدم اعتماد به نام یا MIME اعلامی مرورگر
- عدم نمایش اطلاعات حساس کاربر بیش از نیاز نقش
- audit log تغییرناپذیر برای ورود ادمین، تغییر نقش، تعلیق و moderation
- اعلان برای عملیات حساس و امکان revoke نشست‌ها
- رفع مسیر تغییر رمز بدون توکن و endpointهای فاقد ownership پیش از انتشار عمومی

## فازهای پیاده‌سازی

### فاز A — Backend hardening

رفع مجوزها، ساخت نقش‌ها، endpoint پروفایل مدرس امن، مدل Ticket/Message/AuditEvent و تست‌های امنیتی.

### فاز B — پشتیبانی کاربر

فرم گزارش مشکل، فهرست تیکت‌های کاربر، شماره پیگیری و گفت‌وگوی دوطرفه.

### فاز C — پنل عملیاتی

صف تیکت، تخصیص، فیلتر، یادداشت داخلی، SLA و تاریخچه تغییرات.

### فاز D — moderation و مدیریت

تأیید مدرس، محتوای گزارش‌شده، تعلیق کنترل‌شده و audit viewer.

### فاز E — observability

داشبورد نرخ خطا، زمان پاسخ، تیکت‌های پرتکرار و اتصال گزارش کاربر به شناسه رویداد سمت سرور؛ بدون ذخیره داده حساس در لاگ‌ها.

## معیار پذیرش نسخه واقعی

- کاربر واردشده بتواند گزارش را ثبت و وضعیتش را دنبال کند.
- Support نتواند به عملیات Admin دسترسی پیدا کند.
- هیچ مدیر نتواند عملیاتی خارج از نقش خود را با فراخوانی مستقیم API انجام دهد.
- هر تغییر حساس شامل actor، زمان، هدف، مقدار قبل/بعد و دلیل باشد.
- پیوست نامعتبر یا بیش‌ازحد مجاز در هر دو سمت رد شود.
- مسیر اصلی تیکت و moderation تست end-to-end و تست مجوز منفی داشته باشد.

## تصمیم MVP فعلی

در نسخه تمرینی، صفحه ادمین و فرم گزارش نمایشی اضافه نمی‌شود؛ چون backend فعلی قرارداد امن لازم را ندارد. معماری فرانت طوری نگه داشته می‌شود که پس از آماده‌شدن APIها، route group مستقل ادمین، layout محدودشده و queryهای جداگانه بدون بازنویسی صفحات عمومی افزوده شوند.
